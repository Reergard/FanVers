# Повідомлення про помилку в тексті книги (бекенд)

Коротко: залогінений читач може надіслати **репорт** — збережений запис про знайдену помилку в **конкретному розділі** книги. У базі це окрема таблиця; **власник книги** отримує **запис у своїх повідомленнях** (модель `Notification`), прив’язаний до цього репорту. Окремої розсилки на email для цього сценарію немає.

---

## 1. Де що лежить у коді

| Що | Де |
|----|-----|
| Модель репорту | `apps/editors/models.py` — `ErrorReport` |
| API репортів | `apps/editors/api/views.py` — `ErrorReportViewSet`, `apps/editors/api/serializers.py`, маршрути в `apps/editors/api/urls.py` |
| Повідомлення власнику | `apps/notification/signals.py` — сигнал після створення `ErrorReport` |
| Віддача даних у списку повідомлень | `apps/notification/api/serializers.py` — `NotificationSerializer` |
| Завантаження зв’язків у списку | `apps/notification/api/views.py` — `select_related` для `book`, `error_report`, користувача репорту, розділу |
| Повний опис REST повідомлень (`list`, `version`, права, сигнали) | **`docs/NOTIFICATIONS_BACKEND.md`** |

Підключення URL: префікс **`/api/editors/`** (див. `apps/api/urls.py`).

## 2. Модель `ErrorReport`

Один рядок = один репорт від одного користувача по одній парі «книга + розділ» у момент відправки.

- **`user`** — хто надіслав (ставиться на бекенді з сесії, не з тіла запиту).
- **`book`**, **`chapter`** — до якої книги та якого розділу стосується зауваження.
- **`error_text`** — зазвичай **виділений фрагмент** тексту (як його передає клієнт).
- **`suggestion`** — довільний текст; фронт кладе сюди **тип помилки** (українською) і за потреби **коментар** у зручному для парсингу на клієнті вигляді (рядки на кшталт `Тип помилки: …` та блок `Коментар:`).

Перевірка узгодженості: розділ має належати тій самій книзі, що й `book_id` — це робить серіалізатор.

## 3. REST API репортів

**Базова адреса:** `POST/GET /api/editors/error-reports/`  
(для одного запису також `GET /api/editors/error-reports/<id>/` — як у звичайному ViewSet.)

**Доступ:** тільки **авторизований** користувач (`IsAuthenticated`).

**Що дозволено методами:**

- **Створити** репорт (`POST`).
- **Подивитися список** репортів, де користувач або **власник книги**, або **автор репорту** (щоб бачити свої відправки та репорти по своїх книгах). Для однакових умов використовується один запит з `Q` та **`.distinct()`**, щоб один рядок не потрапив у відповідь двічі.
- **Подивитися один** репорт за id, якщо він підпадає під той самий фільтр.

**Немає** окремих ендпоінтів на редагування чи видалення репорту з цього набору (немає `update` / `destroy` у цьому ViewSet).

### 3.1. Тіло `POST` (як очікує серіалізатор)

Клієнт передає зручні поля:

- `book_id`, `chapter_id` — числа;
- `error_text`, `suggestion` — тексти.

Перед збереженням `book_id` / `chapter_id` перетворюються на зв’язки `book` / `chapter` і з валідованих даних прибираються, щоб у модель не потрапили зайві ключі.

### 3.2. Додаткова перевірка в `create` в’юсета

Перед викликом стандартного створення перевіряється, що книга існує і що в неї **є власник** (`book.owner`). Якщо власника немає — повертається зрозуміла помилка (на кшталт «у книги немає перекладача»), бо кому надсилати повідомлення в такому випадку невизначено.

## 4. Як з’являється повідомлення власнику

Після успішного збереження нового `ErrorReport` спрацьовує сигнал **`post_save`** у `apps/notification/signals.py`:

- якщо це **новий** запис (`created`);
- якщо у книги є **власник**;

створюється **`Notification`**:

- **`user`** = власник книги;
- **`book`** = та сама книга;
- **`message`** = короткий текст українською (хто і про яку книгу);
- **`error_report`** = посилання на щойно створений репорт.

Так власник бачить рядок у `/messages` і може відкрити деталі, не чіпаючи окремо таблицю репортів у адмінці (модель репорту в стандартну Django admin у проєкті окремо не обов’язково зареєстрована — орієнтуйтеся на актуальний `apps/editors/admin.py`).

**Важливо:** сповіщення створюється **тільки сигналом**. У в’юсеті репорту дубль не додається — одне місце відповідальності.

## 5. Що віддає API повідомлень про репорт

У `NotificationSerializer` для записів з прив’язкою до репорту додано зручні для UI поля (частина — через методи, щоб безпечно обробляти відсутній `error_report`):

- `error_report_id`
- `reporter_username` (логін того, хто надіслав репорт)
- `book_title`
- `chapter_title` (назва розділу з репорту)
- `error_text`, `suggestion` — з моделі `ErrorReport`

Список повідомлень підвантажує потрібні зв’язки одним запитом (`select_related`), щоб не робити десятки звернень до БД на кожне повідомлення.

---

## 6. Зв’язок із підтримкою (для орієнтиру)

Загальні звернення в підтримку — це **інший** потік (`SupportTicket`, email staff тощо). Репорт помилки в тексті — **окремий** механізм: цільова аудиторія повідомлення — **власник книги** через внутрішні повідомлення сайту.
