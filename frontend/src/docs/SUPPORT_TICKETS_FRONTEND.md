# Звернення в підтримку (Frontend)

## Навіщо це

Сторінка **`/support`** дає користувачу форму: тип звернення, коротка тема, текст, для гостя — ім’я та email; можна додати до **трьох** файлів. Після відправки показується **номер звернення**; за потреби форма ховається, з’являється кнопка «Нове звернення».

## Файли

| Що | Файл |
|----|------|
| Сторінка форми | `src/info/help/support.tsx` |
| Стилі блоку допомоги | `src/info/help/HelpPages.module.css` |
| Базовий URL API | `src/api/endpoints.ts` → `supportTickets: "/api/support/tickets/"` |
| HTTP-клієнт (CSRF, JWT, retry) | `src/api/http.ts` |

Маршрут у поточному коді: `App.tsx` — шлях `/support`, lazy-імпорт `./info/help/support`.

## Як відправляється запит

1. Перед відправкою викликається **`fetchCsrfToken()`** (`src/auth/csrf.ts`), щоб у заголовку був `X-CSRFToken` (як для інших POST на цей бекенд).
2. Якщо **немає файлів** — тіло **JSON** (`Content-Type: application/json`): `category`, `subject`, `message`, `website` (honeypot), `page_url` (поточний URL, обрізаний), для гостя ще `name` та `email`. Для **залогіненого** поля `name`/`email` **не** відправляються: на бекенді для збереження використовуються **`user.username`** (ім’я/нік) та **`user.email`**.
3. Якщо **є файли** — **`FormData`** (тип контенту ставить axios сам): ті самі поля + кілька разів `append("attachments", file)`.

Інтерцептор у `http.ts` додає `Authorization: Bearer …`, якщо є access-токен, і CSRF для «небезпечних» методів.

## Поля форми та поведінка

- **Тип звернення** (`category`) — збігається з кодами бекенда: `technical`, `payment`, `content`, `account`, `suggestions` («Пропозиції та побажання»), `other`. Вибір — `PillDropdownSelect` (не нативний `<select>`).
- **Коротка тема**, **повідомлення** — попередня перевірка довжини на клієнті; остаточна — на сервері.
- **Гість**: ім’я та email обов’язкові в клієнтській валідації.
- **Залогінений**: показуються **тільки для читання** нік і email з профілю. Стан **`profileLoadedOk`** стає `true` лише після **успішного** `getMyProfile()`. Якщо профіль не завантажився (мережа тощо), форма **не** блокується лише через це — перевірка email лишається на бекенді. Блок на клієнті лише якщо профіль **успішно** завантажений і email **порожній** — тоді показується підказка піти в налаштування профілю.
- **Файли**: якщо користувач обрав **більше ніж 3** файли одразу, показується помилка під полем, вибір скидається (нічого не відкидається «тихо»).
- **Honeypot** `website` — приховане поле, завжди порожнє в нормальному сценарії.

## Стани інтерфейсу

- Кнопка відправки — **`ActionButton`** з `loading` / `disabled` під час запиту.
- Успіх: `ticket_number` з відповіді, повідомлення про прийняття, **`resetFormAfterSuccess`** (скидання полів, для гостя — ім’я/email).
- Помилки: `formatApiErrors` розбирає відповідь сервера; у списку полів є **`attachments`**, щоб показувати текст помилок по файлах.
- **429** (занадто багато спроб / дедуп) — окреме повідомлення.
- Після успіху форма **прихована**, показується блок успіху та кнопка **«Нове звернення»** (скидає `successTicket` і знову показує форму).

## Зв’язок із проксі та продакшеном

У поточній конфігурації: у **dev** (`vite.config.ts`) проксується `/api` на `http://127.0.0.1:8000`; у `http.ts` для dev `baseURL` axios порожній (`import.meta.env.DEV`), тож запити йдуть на той самий origin, що й фронт. У **prod** базовий URL береться з `import.meta.env.VITE_API_BASE_URL` (див. `http.ts`).
