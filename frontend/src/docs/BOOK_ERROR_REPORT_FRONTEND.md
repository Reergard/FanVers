# Повідомлення про помилку в тексті книги (фронтенд)

Коротко: на сторінці **читання розділу** користувач може повідомити про помилку в тексті: виділити фрагмент, підтвердити, заповнити коротку форму й надіслати на сервер. **Власник книги** потім бачить це у **повідомленнях** (`/messages`) і може відкрити модалку з деталями.

---

## 1. Де що лежить у коді

### Сторінка розділу та форма репорту

| Файл | Роль |
|------|------|
| `catalog/ChapterDetailRouter.tsx` | Завантажує дані розділу, передає в `ChapterDetail` ідентифікатори книги/розділу та назви для репорту. |
| `catalog/ChapterDetail.tsx` | Кнопка з SVG-рамкою «Повідомити про помилку», режим виділення тексту в блоці читання, підтвердження, `Escape` / «Скасувати», відкриття модалки. |
| `catalog/ModalErrorReport.tsx` + `ModalErrorReport.module.css` | Модалка: фрагмент, тип помилки (радіо), коментар, відправка. |
| `api/errorReportApi.ts` | Збір тіла запиту під поля бекенда (`error_text`, `suggestion`) і `POST` на ендпоінт репортів. |
| `api/endpoints.ts` | Константа URL репортів (`errorReports`). |
| `api/http.ts` | Спільний axios: токен, CSRF, повтор після refresh — усі POST репортів йдуть через нього. |

### Повідомлення власнику

| Файл | Роль |
|------|------|
| `notification/NotificationsPage.tsx` | У списку для записів з `error_report_id` — посилання-кнопка на деталі; модалка з полями репорту. |
| `notification/notificationsService.ts` | Завантаження списку з **нормалізацією** полів; `getNotificationById` для повного об’єкта одного повідомлення. |
| `notification/parseErrorReportSuggestion.ts` | Розбір рядка `suggestion` з API на **тип помилки** (рядок після `Тип помилки:`) та **коментар** (після `Коментар:`). |
| `notification/types.ts` | Тип `AppNotification` з опційними полями для репорту. |

Загальний опис сторінки `/messages` — **`NOTIFICATIONS_FRONTEND.md`**; REST і версії на бекенді — **`backend/docs/NOTIFICATIONS_BACKEND.md`**. Тут лише «гілка» репортів.

---

## 2. Потік на сторінці розділу

1. Користувач натискає **прозору кнопку** поверх декоративної рамки (текст на кнопці малює SVG, не дубльований HTML-текстом).
2. Якщо **не залогінений** — відкривається модалка входу з поверненням на поточний шлях.
3. Увімкнюється **режим виділення**: підказка «виділіть текст…» і **тільки** «Скасувати». Після `mouseup` у межах тексту розділу зберігається виділений рядок.
4. Коли текст є — підказка **зникає**, з’являється **«Підтвердити вибраний текст»** і «Скасувати»; `Escape` виходить з режиму.
5. Підтвердження відкриває **`ModalErrorReport`** з уже підставленим фрагментом і `bookId` / `chapterId` з даних розділу.
6. Після успішної відправки показується коротке підтвердження (toast), модалка закривається, локальний виділений текст скидається.

При зміні розділу (slug) стан режиму й модалки **скидається**, з `document` знімається слухач `mouseup`, щоб не залишати «вісить» обробник.

---

## 3. Що саме відправляє `errorReportApi`

На сервер у JSON йде:

- `book_id`, `chapter_id` — як очікує бекенд;
- `error_text` — обраний фрагмент;
- `suggestion` — один текстовий блок: перший рядок з **типом** українською (узгоджено з підписами в модалці: Опечатка, Переклад / формулювання, Пунктуація, Інше), за потреби порожній рядок і блок **`Коментар:`** з текстом користувача.

Окремого поля `error_type` на бекенді немає — тип живе всередині `suggestion`, а на сторінці повідомлень **парситься** для зручного показу.

---

## 4. Потік для власника на `/messages`

1. У списку повідомлень, якщо є **`error_report_id`**, після основного тексту показується кнопка на кшталт «подивитися деталі помилки».
2. По кліку відкривається **модалка**. Щоб підтягнути повні поля (тип, фрагмент, коментар, назва розділу), для таких записів додатково викликається **`GET` одного повідомлення** за id (той самий серіалізатор, що й у списку, але гарантує актуальний об’єкт).
3. У модалці показуються: хто знайшов, дата, книга, розділ, **тип помилки** (з парсера), **фрагмент**, **коментар** (решта з `suggestion`). Якщо старий запис без префікса `Тип помилки:`, усе тіло `suggestion` може потрапити в блок коментаря, а тип — «—».

---

## 5. На що звернути увагу при змінах

- Будь-яка зміна **формату** рядка `suggestion` на фронті при відправці повинна узгоджуватися з **`parseErrorReportSuggestion`**, інакше тип/коментар на `/messages` роз’їдуться.
- Репорти — **не** тикети підтримки; інший UX і інший API.
- Для роботи потрібні валідні **сесія / токен** і (для POST) **CSRF**, як для інших небезпечних методів через `http.ts`.
